# Current-season data snapshots

The refresh command is `python -m backend.scripts.refresh_current_data --season 2026`. Run from the project root with the development virtual environment activated. Downloads use the existing nflreadpy dependency; there are no paid services or new dependencies. The script fails with a nonzero exit on missing source data, unsupported schema, ambiguous membership, mismatched schedule, unknown scoring inputs, or target-day/future statistics. It requires the original historical player and schedule files for the first publication. It does not retrain models or change Task 1–3 exports.

Sources are the official [nflreadpy load functions](https://nflreadpy.nflverse.com/api/load_functions/) and [nflverse weekly-roster contract](https://nflreadr.nflverse.com/reference/load_rosters_weekly.html). Actual inspected roster fields include `gsis_id`, `full_name`, `season`, `week`, `game_type`, `team`, `position`, and `status`. GSIS IDs match the weekly statistics' `player_id`. Only regular-season RB/WR membership is normalized. The source status is retained as `roster_status`; recommendations require `ACT`. The code does not translate roster codes into injury diagnoses or game-day guarantees.

The publisher merges refreshed-season statistics/schedules with other existing seasons, validates using the original pipeline, writes Parquet files and a manifest into a new `data/snapshots/<id>/` folder, then switches `data/current.json` using a same-directory atomic replacement. Failed publication cannot expose half-written data to API startup. Earlier roster observations remain in the next snapshot, with the newest eligible observation selected per player/week. Do not run multiple refresh writers simultaneously. Old generation folders are retained for audit/recovery and can consume disk over time. The artifacts are local and Git-ignored; regenerate them on another machine.

The repository loads the manifest once at startup. Explicit `FANTASY_PLAYERS` or `FANTASY_SCHEDULES` overrides opt out of it as a unit, avoiding accidental mixing of generations. Historical fallback does not imply current-season readiness. Health exposes actual loaded model and snapshot metadata. After refresh, restart the API to reload files/models and invalidate all inference caches.

Weekly effective labels identify membership for that week; they are not transaction effective timestamps or source publication timestamps. `observed_at` records our download observation, never a guessed earlier time. Eligibility requires the correct week's snapshot to have been observed before the game's midnight UTC boundary, with an age of at most seven days. This intentionally rejects historical games when only a later first observation exists, unknown future-week rosters, same-day roster observations, and stale snapshots. Already played games in the current week can therefore be listed as unavailable while upcoming games have projections. Accurate historical transaction timing would require another verified, timestamped source; no such timing is fabricated here.

Tests use tiny local fixtures for atomic failure preservation, source schema ambiguity, observation retention, status filtering, rookies with no statistics, trade/team changes, first-week veterans with prior-season history, stale rosters, missing future-week coverage, and prevention of retroactive roster use. Existing statistics leakage tests still prove that changing/deleting target and future outcomes cannot affect pregame features. The full suite requires no network.

Remaining limitations: no verified injury/game-day availability feed, no calibrated uncertainty, no automated refresh scheduler, no cold-start rookie model, and no 2026 validation or retraining of ppr-v1. A first refresh requires some current-season statistics to be published; preseason/before-first-game refresh without such statistics is rejected. Source data may contain later statistical corrections. These constraints are exposed rather than replaced with fabricated inputs.
